# Full-scale playtesting plan for Battle

## Scope and evidence

Test the finished player journey from first launch and team creation through the last story choice, a new run, and independent competitive play. Cover each reachable screen, meaningful action, authored branch, irreversible choice and recoverable failure. Record each supported rule, mode and availability boundary. Test whether players discover what to do, apply what they learn to new situations, find more than one satisfying strategy, and choose to return. Use the [game reference](game-reference/README.md) to resolve the affected features from current code, and reconcile the [coverage register](PLAYTEST_COVERAGE_REGISTER.csv) against the build entering testing. The earlier browser and campaign reports provide baselines for comparison. [Coverage review](north-road/INTERFACE_COVERAGE_REVIEW.md) · [Detail review](north-road/INTERFACE_DETAIL_REVIEW.md) · [Previous playtest evidence](HUMAN_STYLE_PLAYTEST.md) · [Existing protocol](PLAYER_TESTING_PROTOCOL.md)

| Lane | Assignment | Evidence it produces |
| --- | --- | --- |
| **Blind** | A player agent uses a fresh browser profile, visible screens, and ordinary input. Give it a goal, its knowledge level, and a device. An accessibility agent can use the designated accessibility surface. | What the agent discovered, expected, tried, misunderstood, skipped, or abandoned. Each battle it enters resolves through ordinary play. |
| **Scripted** | Playwright drives the packaged UI through known states with real clicks, taps, or keys. Isolated checkpoints can stage rare encounters and failures. | Repeatable state, transaction, layout, and navigation evidence, with exact inputs and expected results. |
| **Engine** | Resolve pinned seeds and legal choices in supported formats, run the comparison and mechanics suites, and sweep progression policies. | Determinism, legality, parity, and progression telemetry for the sampled configurations. |
| **Release** | Verify the exact artifact and exercise fresh installs, upgrades, offline operation, two clients, and recovery. | Package digest, verified asset requests, previous and resulting save state, and supported environment specifications. |
| **Participant** | Consenting adult players use a frozen build, with their ordinary devices or access setup where relevant. Include unmoderated home play and matched challenges. | Voluntary sessions, delayed recall, independent learning, interpretation of story and mechanics, meaningful accessibility, and friend-to-friend experience. |
| **Confirmation** | An independent agent receives the starting public state and visible symptom. A separate diagnostic agent may inspect source and logs afterward. | Minimal reproduction, regression assertion, and evidence from the fixed build. |

Label each case or step `blind-visible`, `scripted-visible`, `checkpoint`, `controlled-outcome`, `engine`, `hardware`, `hosted`, or `participant`. Record the actual device and deployment target alongside the evidence label. A checkpoint proves behavior after its entry. A controlled result can prove navigation, reward, and aftermath after that result. Mark combat completion only when the simulator resolves it. Use `pass` or `fail` for a defined criterion, and `observed` for a research case that captures a decision, perception, or reason for stopping. Use `blocked` for unavailable prerequisites, `unobserved` for eligible cases without evidence, and `unsupported` for a demonstrated inapplicable feature or combination. [Session-Based Test Management](https://www.satisfice.us/articles/sbtm.pdf) · [Playwright Trace Viewer](https://playwright.dev/docs/trace-viewer)

## 2. Assign playtest charters and define the rules

Use independent fresh browser contexts with their own storage, settings, viewport, and input. Give testers only their brief, task, starting state, and capabilities. Keep the coverage register, prior findings, future locations, and evaluator's scoring prompts away from them. Agents can use screenshots, click/tap, scroll/swipe, keyboard, and the game’s visible text. For the keyboard or screen-reader charter, allow the designated accessibility surface. Keep source, DOM locators, debug APIs, private state, developer wins, agent walkthroughs, and other agents’ traces in the diagnostic lane. Separate live observation from post-session questioning. Start with two independent runs each for J01 and J03. Use the role brief in one run and a neutral brief with the same goal and starting state in the other. Add a fresh run if agents disagree or the coverage register calls for another configuration. Give each short session about 30–45 minutes or 40–70 meaningful inputs as a planning budget. Long journeys can continue in multiple sessions using the same agent and save. Stop at the goal, credible abandonment, a verified hard blocker, or after three distinct unsuccessful approaches. Budget exhaustion is `unobserved` for the remaining states. The evaluator asks debrief questions after actions to avoid supplying hints. [Exploratory charter design](https://www.satisfice.us/articles/sbtm.pdf)

Give each short task session one primary goal and at most two optional goals. Let the tester choose where to spend time and money, when to backtrack or ask for help, and which optional encounters to ignore. J19 and J20 follow an open schedule with no assigned tasks. Use the Section 9 protocol for their consented records and end-of-window interview. J25 runs to its generated action budget. Record the visible event that preceded hesitation or mistakes. Let the game run at normal speed for timing, performance and time-limited activities. Label any slow observation session separately. Carry only the tester's own notes and save between sessions. If a battle is skipped to expose downstream content, fork a copy into the scripted lane and preserve the unresolved blind journey.

Use an independent pass for high-impact findings. Give that agent the same public starting state and goal without the suspected cause or prior click sequence. Give repeatable technical findings to the diagnostic lane for reduction. The resulting fixture should fail on the affected build and pass on the repaired build. Keep visible confusion, reproducible gameplay defects, and taste judgments as separate evidence. Benchmarks for automated bug finding and visual game completion support using these checks together. [GBQA](https://arxiv.org/abs/2604.02648) · [VideoGameBench](https://vgbench.com/)

## 9. Test voluntary play, learning, strategy and access

### Unmoderated free play and multi-day return · J19–J20

Start with a seven-day qualitative pilot of roughly 6–10 consenting adults spanning newcomers, main-series fans and competitive players. Give each a fresh profile on their usual device and the neutral J19 brief. Run this before the same people see directed tasks, other builds, actual secret locations or the test register. Let players choose the mode, time, session length and stopping point. Collect an optional short note after a session or consented session markers. Ask for a debrief after the observation window so a reminder cannot become the reason for returning.

Record first self-chosen goal, first meaningful action, modes and detours tried, save point, skipped scenes, reason for leaving, voluntary returns and first action on return. Among players who return after a gap, capture how they locate their bearings. Where feasible, sample the 24–72 hour gap. Ask them to describe their goal, the last meaningful story choice and a memorable character or encounter before showing their prior notes or a recap. Ask whether they want to continue or start a different run, and record their subsequent choice if observed. Include people who stop early or never start. Store the study window and denominator for every reported observation. ### Learning transfer across experience groups · J21

Match the seed, difficulty, unlocked resources, device class and instruction across Pokémon newcomers, main-series fans and Showdown players. ### Masked design comparisons · J22

## 10. Evidence, metrics, and release gates

For each meaningful step record the build, case and charter IDs, seed or fixture, screen/action/branch ID, mode, device/browser/input, current settings, state before, stated visible expectation, action, happened, state after, next available action, trace frame, timestamp and timing source. Record actions to completion, unexpected actions, accidental commits, backtracks, failed attempts, requests for help, missing cues, skipped content, and stopping reason. State the denominators. Use actual state changes for technical outcomes and notes for subjective reactions. Keep artifacts per release and per session, with protected fields removed before sharing.

Use a standing evidence folder such as `agent-state/playthrough/full-scale/<release-id>/`. Keep a trace and action log for scripted and blind-agent sessions. For participants, keep consented notes, diary events and media where available, plus the actual study window. Track checkpoint and controlled-outcome scope alongside visible steps. Report progress as covered/eligible cases by workstream, then supported environment, with blocked, failed and unobserved counts visible. A blind task counts as assisted once any route hint is given. Track first meaningful action, success unaided, hint use, wrong turns, frustration cues and abandonment by charter. For comparisons and sampling, record assignments, cohort or seed counts, measurements, excluded and unfinished attempts, and the reason for any follow-up. Give disagreements their own confirmed or open report after a fresh rerun.

| Finding level | Evidence and gate consequence |
| --- | --- |
| P0 | Save/data loss, permanent progression block, exposed private competitive information, crash loop, or repeatable unauthorized loss. Block the affected release scope and confirm preservation in a clean environment. |
| P1 | Wrong battle outcome, incorrect economy/input state, required inaccessible control, broken continuation, or app/package failure on a supported target. Require a reproduce-and-fix pass plus adjacent regressions. |
| P2 | Repeated confusion, unclear next step or inaccurate feedback with a workaround, avoidable loading or timing regression, or substantial visual inconsistency. Record effect and affected configurations and retest when repaired. |
| P3 | Optional presentation or taste observation. Keep it linked to the frames and tasks that informed it. |

Produce a coverage register, blind transcripts, screenshot/video gallery, seed/fixture and rule matrix, timing and data report, bug register and retest results, and a one-page release decision. A confirmed bug has the smallest reproduction, expected and actual outcome, impact, source/evidence, fixed build, and a regression. Use a fresh blind rerun for changed navigation, comprehension or story framing.

For the fix loop, replay the original symptom, rerun shared controls or state transitions, then sample downstream milestones with an affected save. Keep the earlier result and mark the repair with its new digest. Prioritize first progression blockers and lost state, then battle correctness and access to core controls, then repeated orientation and readability problems. Each round closes only when the assigned case and its required nearby cases have current evidence. Release results must come from the final candidate.

Before recommending technical release readiness, verify the same packaged digest, required regression and playable inventory coverage, offline save and rule parity checks, and zero unresolved P0/P1 defects in the intended release scope. Separately summarize field validation on the same build or identify the exact build and changed flows. Give open participant, hardware, hosted and localization cases an owner and a concrete blocker or next step. Any confirmed P0/P1 from field or participant work affects the technical release gate. Use real-player evidence for voluntary return, audience response and lived accessibility. [Human usability testing](https://www.gov.uk/service-manual/user-research/using-moderated-usability-testing) · [Packaged playtest gate](../scripts/debug/release-candidate-playtest.sh)
