# Battle interface coverage review and implementation gates

This review extends the interface plan against live 2.0.5. It covers the shipped build at game commit `6f1716f`, the release test follow-up `c0d54b5`, and asset digest `e6ef05cdec5646da`. The audit found several failures that take priority over visual migration. The revised register assigns cases to every reconciled catalog entry. Those cases still require execution on the implementation candidate. [Interface plan](INTERFACE_UNIFICATION_PLAN.md) · [Playtest register](../PLAYTEST_COVERAGE_REGISTER.csv) · [Shipped deployment](https://github.com/merogith/battle/actions/runs/45893048695)

## How the review was divided

Two leads owned independent reviews. The experience lead reconciled facilities, activities and progression with a service reviewer, and campaign geography, story, audio and replay with a narrative reviewer. The engineering lead reconciled battles, selection rules and generated data with a combat reviewer, and app navigation, settings, save, offline and publishing with a platform reviewer. The final reconciliation compared their reports with current source, the shipped package and the existing test register. Keep the same separation during implementation. Each change needs a reviewer who follows the neighboring entry or return path and a reviewer who checks the state owner affected by the change.

Use four evidence types throughout. **Inventory** means the code, asset or authored ID has an owner and a case. **Source or fixture reproduced** means code or a controlled scenario showed the stated behavior. **Packaged play** means a player-facing control exercised the state on the candidate artifact, with fixture boundaries and resulting state captured. **Physical or player observation** means the claimed input, installation, perception or decision was actually observed on the relevant setup. A case can require more than one type. Record each separately. [Full-scale test protocol](../FULL_SCALE_PLAYTEST_PLAN.md) · [Release evidence template](RELEASE.md#evidence-template)

## Order of implementation

1. Repair silent startup, unsafe transactions, online results and active save or archive mixing. Include confirmation when approval is unavailable, stale restore reviews, shared opponent visibility, and partial optional-media updates. Protect the existing authored story before running the generator. Reproduce the reported failures first and capture the corrected state owners in fixtures. [Detail findings](INTERFACE_DETAIL_REVIEW.md#code-findings-at-the-same-level)
2. Fix shared navigation, focus, notification placement and small-screen controls. Finish the Pallet shop loop, the dense Tutor return loop, and the road-to-battle-to-town loop as the visual references.
3. Migrate services, training and field tools through the same control and transaction patterns. Then migrate optional play, all story families and postgame through authored scene briefs. Measure slow loading and repeated renders by family before removing legacy rules.
4. Apply the shared control language to battle entry, local and online modes, Arena, recovery and installer. Run the reconciled register on the verified artifact with the required failure, replay, device and hosted cases assigned. Review each surface family and recorded player response before treating this as a release candidate.
