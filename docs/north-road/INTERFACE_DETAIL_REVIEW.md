## How to decide whether an element belongs

Give each distinct displayed element a job before approving the screen. It may orient the player, offer an action, explain a real decision, report what happened, make the interface accessible, or convey something specific about the world. An illustration can establish a place. A pause can give an earned event room. A small border can group a product with its price. Put the job in the review record, with the affected state and the source owner. Decide to **keep**, **combine**, **show when needed**, or **remove**. When two elements have the same job, keep the one that a player can find and act on at the right time.

Follow the smallest unobvious details. Record which view owns a badge or hint, where its words come from, and when it is read or dismissed. Check that a price, destructive consequence, pending reply, turn limit, battle accuracy, exact move effect, or earned reward remains accessible at the decision point. Use plain action names, an accurate explanation for a real lock, and a stable way back to the same place. A change should preserve focus, selected Pokémon, legal actions, source data and committed state. [Player tasks](PLAYER_EXPERIENCE.md) · [Attachment and focus checks](../../tests/visual/keyboard-navigation.mjs)

Give each existing content variant a state and evidence link. For each repeated surface, record first visit, revisit, ready, empty and locked, selected, pending, successful, canceled, failed and ended as applicable. Record at least one visible representative per source family and enumerate the finite variants with catalog and property checks. Review protected alternatives like screen reader labels, large type, touch-only, reduced motion, Instant, mute, no-art, offline, narrow landscape and browser Back on the actual route. Mark every remaining variant explicitly in the implementation ledger, with a route to exercise it. [Device and access evidence](RELEASE.md#3-physical-devices-accessibility-and-human-testing)

## Engineering review at implementation time

Review each extracted constructor, visible copy write and state-changing handler as a linked unit. Use existing modules for pure formatting or effects before adding an abstraction. Separate authored data, render state and gameplay state when they have different lifetimes. Preserve the legal owner of price, effects, RNG, queues, animation cancellation, events, confirmation and save. Remove an old selector, redundant preference listener or obsolete bridge only after verifying its dynamic callers, fallback path and saved-version compatibility. Check which rule actually wins on each viewport before deleting duplicate CSS. [Inline source map](INTERFACE_COVERAGE_REVIEW.md#inline-source-ownership)

Measure actual issues before optimizing. Start with repeated layout and focus churn, avoidable loading and interaction stalls. For each measured change, record a reproducible current trace, the same scenario afterward and the protected results. Capture first request, cold and warm bytes, time until the first usable action, expensive layout work and retained objects after repeated use. Rank by player effect. Keep authored data generation, battle simulation, action handling and accessibility tests separate from presentational performance so a cosmetic speedup cannot conceal a rule change. [Performance benchmarks](../../scripts/debug/perf-bench.mjs) · [Packaged trace suite](../../scripts/debug/release-candidate-playtest.sh)

Remove stale presentation in small reviewed groups. A live probe found the hidden town run chip, badge pips, route track and objective kicker at portrait, short landscape and desktop. They still exist in the DOM. Existing tests reference some of them. First prove the correct heading, landmark, objective and progress can be found through the actual hub and Atlas. Replace old markup-presence checks with those behavioral outcomes, then delete only unused elements and rules. Apply the same procedure to duplicated header and footer buttons, hidden panel shells and unused page-specific decorations. [Town renderer](../../battle.html#L58739) · [Hide rules](../../world-location.css#L155) · [Existing progress test](../../tests/suites/city-route-progress.test.js)

The acceptance record for an edited detail includes its job, owner, states, source, visual and behavioral evidence, and any remaining untested variant. Offer a real scenario before calling a change an improvement. Examples include a new player finding the right item without extra prompts, a keyboard player returning to the saved selection, and a returning player remembering what happened at the gate. Keep broad syntax, package and unit results alongside those observations. [Player charters](../FULL_SCALE_PLAYTEST_PLAN.md#9-test-voluntary-play-learning-strategy-and-access)
