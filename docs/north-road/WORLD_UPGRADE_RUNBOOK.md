# North Road world upgrade implementation runbook

[Coverage audit](WORLD_COVERAGE_AUDIT.md) · [Art and sound direction](PRESENTATION.md#6-world-presentation-plan) · [Release procedures](RELEASE.md) · [Asset assignments](../../design/world-upgrade/scene-assets.csv) · [Prepared files and verification data](../../design/world-upgrade/kit-manifest.json)

**Baseline** `5a05e63` / Battle 2.0.4. Upgrade every player-facing scene and return path, from a fresh title to the Crucible and the separate battle modes. The game is an illustrated journey with direct inputs. Players read a place from its landmark, a person from the work they are doing, and a consequence from what has visibly changed. The stage supports a short prompt and the next useful action. A small atlas connects existing places and return paths.

The implementation must preserve the current campaign steps, earned resources, selected partners, legal battle requests, seed outcomes, save compatibility and release/update behavior. The identified missing travel trigger and mismapped art are corrections to presentation. The story section specifies intentional choices about dormant authored material. Gameplay, app and save changes start when this runbook is implemented.

### Reusable screen and scene contract

1. **Resolve context before entry.** Get the legal place, stable event ID, mode, active trainer and lead from existing state. Keep array offset and persistent event ID distinct. A backdrop, lighting and soundtrack can change as a consequence of that state. Use the current actor, species, actual form/shiny and existing front or back resolution. A missing asset displays the same name, legal choices and purpose with a fallback.
2. **Lay out the current action once.** Set the place and status in a short header and give the illustration one clear subject. Then show the current prompt or useful fact and a stable action footer. Use the same hierarchy for choice, inspect and confirmation. On narrow portrait use an art band above the controls. In short landscape put art beside the content or reduce it to a small header. At larger sizes widen the stage around a bounded text column. Keep a 44 CSS-pixel actionable target, visible focus, normal scroll and safe-area padding. Test in the browser at 320×568, 568×260, 820×1180 and 1440×900. On larger text, the content area grows or scrolls while Back and the intended action remain reachable.
3. **Show details on request.** A mandatory fact stays with its action. Optional tutorial, rules, field tips, dialogue backlog, advanced filters and build details retain their own entry. Keep the same selected partner, focus, filters, scroll and inventory context when a detail returns. One distinct speaker label and at most one relevant prop or shot accompany a line. The player can advance, read instantly, or open the backlog where the source supports it.
4. **Commit only through the existing operation.** Show a preview for any spend, reward, permanent decision or actual choice. Confirm calls the existing transaction once. Lock duplicate input while it resolves. Display completion from committed state. If the operation fails, preserve the input and show a route to retry. Back before confirmation preserves the original state. Return after a success points to the changed place, item, partner or next match.
5. **Stage and mix on state changes.** Keep one optional background score, one room or location ambience and limited one-shots, with effect, score and voice volumes respected. Play a cue once per meaningful change. Use one simple movement for a routine action and hold longer for major player-controlled thresholds. Reduced motion and instant settings render the final composition and real controls immediately. Give captions or labeled props for cues whose information matters. End visual work and release audio when leaving its owner.
6. **Verify every state, then remove competing prompts.** Exercise first use, return, locked, empty, cancel, success, failed write, refresh, muted and missing-file cases applicable to each family. Players should know where they are, what to do and why the state changed at native speed on a phone. Use named work and evidence keys from the audit so a new scene or modal cannot bypass the coverage gate.

### Candidate timing and visual rules

- A button confirms immediately. Target 80–180 ms for local feedback, 160–240 ms for an ordinary view transition, and 250–450 ms for a composed doorway or important trainer reveal. These timings apply to effects. Input and legal options remain synchronized to commit and native battle events. Story holds end on player input and present a safe Skip when available.
- Screen art has one subject and a quiet lower or side text area. Warm light identifies inhabited places, cold highlights identify exposed or abandoned spaces. Use sparing bright colors for the next action, committed rewards or warnings, with text and icon for the same meaning. Readable body type and stock controls must survive missing media. Keep tall affordances, consistent Back, separate danger actions and no line of optional copy that repeats the button.
- For a scene profile, map place/event, preferred asset, crop, fallback and optional cue through existing selectors. Keep one source for title version, current checkpoint, switch target, trainer assignment and transaction state. Reuse storyboard, dialog, Summary, sprite and playback paths. Introduce new data only for art placement, camera, cue or explicit newly reachable story conditions.
